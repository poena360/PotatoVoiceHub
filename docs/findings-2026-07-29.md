# 実機検証結果 — A.I.VOICE2 Editor 2.14.1

検証日: 2026-07-29
検証環境: Windows 11 Pro 26200 / A.I.VOICE2 Editor **2.14.1** / 紲星あかり(NV) 2.0.1
対象コード: gizagizamax/PotatoVoiceHub `PotatoVoiceHub` ブランチ HEAD `f3ba895`

> A.I.VOICE2 には公式APIが無く、GUI を外から操作するほかに手段が無い。

> 書かれたコードが、Editor の実装変更で前提を失っていた。**
> 検証していないバージョンについては不明。
>
> A.I.VOICE1 経路（公式 API 使用）は検証対象外。A.I.VOICE1 の API を叩いている箇所そのものは
> 触っていないが、クリップボード監視・例外処理・ログ・終了処理といった
> **両方が通る共通部分は変更している**ので、そこは A.I.VOICE1 でも動作確認が要る。

## 結論サマリ

調査開始時は「A.I.VOICE2 Editor は WPF アプリで、UI Automation でボタンを操作できる」
という前提で計画を立てていた。2.14.1 の実機で確認したところ、前提が変わっていた。

| # | 当初の前提 | 2.14.1 での結果 |
|---|---|---|
| 1 | Editor は WPF アプリ | **Flutter アプリだった**（`FLUTTER_RUNNER_WIN32_WINDOW` / `FLUTTERVIEW`） |
| 2 | ボタン操作は UI Automation で動作している | **UIAツリーが空**で、2.14.1 では UIA 経由で要素を引き当てられない |
| 3 | テキスト領域が `ValuePattern` を持てば SendKeys を排除できる（中心仮説） | ValuePattern 以前に UIA 要素が無いため成立しない。ただし **別ルートで目的は達成できた** |
| 4 | フォーカス奪取はテキスト投入のためだけに必要 | ✅ その通りだった。かつ **フォーカス不要の投入手段が見つかった** |

**総括: 当初の改善方針（UIA のパターン経由でテキストを投入する案）は 2.14.1 では成立しない。
一方で、目標である「フォーカス奪取の全廃」と「サニタイズの縮小」は、
MSAA + PostMessage 経路で達成できることを実機で確認した。**

## 1. A.I.VOICE2 Editor 2.14.1 は Flutter アプリである

ウィンドウ構成:

```
hwnd 34542218  class FLUTTER_RUNNER_WIN32_WINDOW   ← Process.MainWindowHandle
  └ hwnd 3740498  class FLUTTERVIEW                ← アクセシビリティの実体はこちら
```

`FLUTTER_RUNNER_WIN32_WINDOW` は Flutter の Windows ランナーテンプレートが生成する
トップレベルウィンドウクラス、`FLUTTERVIEW` は Flutter エンジンの描画・入力用子ウィンドウ。

当初は「WPFではトップレベルHWNDが1つしかなく子コントロールにHWNDが存在しない」という前提で
考えていた。フレームワークは違っていたが、**制約としては同じ**（Flutter も全描画が1つの子HWND上の
キャンバスで、個々のコントロールにHWNDは無い）。

## 2. UIAツリーは空である — 2.14.1 では UIA 経由の操作が成立しない

同一プロセス・同一タイミングでの比較:

```
MSAA (IAccessible)  : 83 要素
UIA (System.Windows.Automation) : 0 要素
```

- `AutomationElement.FromHandle(top).FindAll(Descendants, TrueCondition)` → **1**（`FLUTTERVIEW` Pane のみ）
- `AutomationElement.FromHandle(flutterView).FindAll(Descendants, TrueCondition)` → **0**
- `TreeWalker.RawViewWalker` でも同じ
- MSAA を先に有効化し、`IAccessible` の参照を保持したまま UIA を叩いても変わらず 0
- MSAA→UIA ブリッジは Flutter の IAccessible ツリーを橋渡ししていない

`Aiv2EditorElem` は `System.Windows.Automation` を利用していたため、帰結として:

| メソッド | 2.14.1 での実際の挙動 |
|---|---|
| `GetElemAiv2Play()` | 常に `null`（`FLUTTERVIEW` は `再生\|停止` にマッチしない） |
| `IsEnabledPlay()` | **常に `false`** |
| `InvokePlay()` / `InvokeWrite1()` / `InvokeWrite2()` | 要素が `null` のため例外になり、`catch` に入って何も起きない |

`MainWindow.xaml.cs` の HTTP ハンドラは `if (!IsEnabledPlay()) → busy` なので、
2.14.1 では `/play` `/saveAudio` `/getStatus` のいずれも `{"status":"busy"}` を返し、
読み上げまで進まない。

> 補足: このコードは 2024年3月〜2026年1月にかけて実際に調整されている
> （README のリリースノート参照）ので、当時の A.I.VOICE2 Editor は UIA を公開していたと思われる。
> Editor 側が Flutter へ移行したタイミングで UIA 経路が成立しなくなった、というのが素直な説明。
> ただし何番のバージョンで移行したかは未確認。

## 3. IAccessible2 系は一切公開されていない

テキスト領域・ボタン・キャラクター項目のいずれについても、`IServiceProvider::QueryService` は全て `E_FAIL`:

```
IAccessible2 / IAccessible2_2 / IAccessibleText / IAccessibleText2 /
IAccessibleEditableText / IAccessibleAction / IAccessibleValue /
IAccessibleComponent / IAccessibleTable2   → 全て hr=0x80004005

Chromium系の a11y スタックで期待できる `IAccessibleEditableText::replaceText` によるテキスト投入は**使えない**。

## 5. 実機で成功した操作（すべてフォアグラウンド奪取なし）

検証中、前面ウィンドウは終始 hwnd 3151138（別アプリ）のままだった。

| 操作 | 手段 | 結果 |
|---|---|---|
| ボタン押下 | `IAccessible::accDoDefaultAction` | ✅ **動作**。キャラクターを NV → 蕾 に切替え、ノード44の表示が実際に変化するのを確認 |
| テキスト投入 | `PostMessage(FLUTTERVIEW, WM_CHAR, ch, 1)` を1文字ずつ | ✅ **動作**。`テストです。これは、投入テスト！` がそのまま入力された |
| テキスト消去 | `PostMessage(FLUTTERVIEW, WM_KEYDOWN/WM_KEYUP, VK_BACK)` × N | ✅ **動作**。空になった |
| アプリ内フォーカス移動 | `IAccessible::accSelect(SELFLAG_TAKEFOCUS)` | ✅ **動作**。キャラクター検索欄にフォーカスがある状態からセリフ欄へ移せる（§8 参照） |

失敗した操作:

| UIA 各種 | ❌ 要素が存在しない |

### WM_CHAR で句読点がそのまま通った意味

現行の `SanitizeText()` の2段階の置換は、**両方とも SendKeys 固有の都合**である可能性が高い
（この時点での見立て。2 は後述の §6 で覆る）:

1. `{ } ~ + ^ % \r \n " ( )` の削除 → SendKeys のエスケープ仕様回避。**WM_CHAR では不要**
2. `。、？！．` → `", "` の置換 → 「句読点があると再生が止まる」への回避策。
   **投入自体は問題なく通ったが、再生時の挙動は未検証**（後述）

## 6. 句読点問題の正体 — Editor本体の仕様だった（再生検証済み）

### 検証結果

同一文章での再生時間の比較（`docs/playback-2.14.1.json`）:

| ケース | 投入テキスト | 音声長 |
|---|---|---|
| A | `今日はいい天気です, 明日は雨が降るそうです, 傘を持って出かけましょう` | **00:06.52**（全文） |
| B | `今日はいい天気です。明日は雨が降るそうです。傘を持って出かけましょう。` | **00:02.16**（1文目のみ） |
| C | B と同じ + ブロックを選択してから再生 | **00:02.16**（変わらず） |

### 原因

**A.I.VOICE2 Editor は `。？！` でテキストを「文」に分割し、再生ボタンは現在の文だけを再生する。**

アクセント編集ペイン（MSAAツリーの index 80 以降）が、現在の文の音素だけを表示していることで確認した:

```
投入: 今日はいい天気です。明日は雨が降るそうです。傘を持って出かけましょう。
  アクセント表示            → 「キョーワイーテンキデス」
  「次の文」ボタン押下後     → 「アスワアメガフルソーデス」
  「次の文」ボタン押下後     → 「カサオモッテデカケマショー」
```

分割文字の切り分け:

| 文字 | 文を分割するか |
|---|---|
| `。` `？` `！` | **する** |
| `、` | **しない**（`今日は、いい天気です` は1文のまま） |

> 追記（実装フェーズ）: 全角/半角を網羅して切り分け直した。
> 分割するのは **`。` `｡` `？` `?` `！` `!` の6文字ちょうど**。
> `、` `､` `．` `.` および改行は分割しない。詳細は §11.1。

### 帰結

- `SanitizeText()` の句読点→カンマ置換は **SendKeys 起因ではなく、Editor本体の挙動に対する
  正当な回避策**だった。「SendKeys の副作用ではないか」という当初の疑いは外れで、
  この置換は必要があって入っていたことになる。
- ただし **`、`（読点）は置換しなくてよい**。読点は文を分割しないので、そのまま投入して問題ない。
  置換対象から外せば読点の「間」が残る。
- `。？！` については、**句読点を保ったまま1文ずつ再生する**方式が実機で動作した:

```
文1: 「キョーワイーテンキデス」    再生 3.20s
文2: 「アスワアメガフルソーデス」  再生 3.35s
文3: 「カサオモッテデカケマショー」再生 3.33s
合計 13.26s（カンマ版は 8.52s / 音声長 6.52s）
```

  手順は 再生 → 完了待ち → `次の文` → 再生 …の繰り返し。
  文数は自前で `。？！` を数えれば求まる。最終文で `次の文` を押しても進まない（安全に終端判定できる）。

  **トレードオフ**: 句読点の抑揚・間を完全に保持できるが、1文あたり約1秒のオーバーヘッドが乗る。
  配信用途では遅延が問題になりうるため、**設定で選べるようにするのが妥当**。

## 7. 書き出しダイアログはネイティブの共通ダイアログ

`書き出し` ボタンを押すと、Flutter ウィンドウとは**別のトップレベルウィンドウ**が開く:

```
7411836   #32770                       名前を付けて保存
34542218  FLUTTER_RUNNER_WIN32_WINDOW  A.I.VOICE2 Editor - (新規プロジェクト)*
```

- `#32770` は Windows 標準の共通ダイアログ。**UIA が完全に効く**（65要素、`ValuePattern` / `InvokePattern` あり）
- ファイル名欄は `AutomationId='FileNameControlHost'` 配下、
  保存ボタンは `AutomationId='1'`、キャンセルは `AutomationId='2'`
- 現行コードが探している `書き出しを実行` という要素は 2.14.1 には無い。
  当時の Editor には独自の書き出しダイアログがあり、2.14.1 で共通ダイアログに変わったものと思われる。

> 追記（実装フェーズ）: この UIA 経路は**採用しなかった**。`AutomationId` が `"1"` / `"2"` の
> 要素はファイルブラウザ内の ListItem とも一致してしまい一意に定まらない。
> ネイティブのコントロールIDで引く方が確実かつロケール非依存だった。詳細は §11.4。

したがって `SaveAudioAiv2()` の書き出し経路は、

1. MSAA で `書き出し` ボタンを `accDoDefaultAction`
2. `#32770` の出現を待つ（プロセスIDでトップレベルウィンドウを列挙）
3. ファイル名欄と保存ボタンを操作

となる。**3 をどう実現するかは、この時点では UIA 併用を想定していた**が、
実装フェーズで Win32 のコントロールIDに変更した（理由は §11.4）。最終形は §11.4 を参照。

> 注意: 共通ダイアログは表示時にフォアグラウンドを奪う。これは Editor 側の挙動であり
> こちらでは制御できない。**書き出し経路だけはフォーカス奪取が残る**。
> 再生経路（`/play`）は完全にフォーカス不要。

## 9. テキスト消去の注意点（実装時の落とし穴）

再生直後はキャレットが文頭に戻るため、**`VK_BACK` だけでは消えない**。
検証中、これで前回テキストが残り新テキストと連結する事故が起きた。

**`VK_BACK` を必要数 + `VK_DELETE` を必要数、両方送ること。**
キャレット位置に関わらず前後とも消え、確実に空になる（実機で確認）。

## 10. 改善方針への影響

テキスト投入方式の候補を、2.14.1 の実測で埋め直すと次のようになる。

| # | 手段 | フォーカス奪取 | エスケープ問題 | 2.14.1での可否 |
|---|---|---|---|---|
| 1 | `ValuePattern.SetValue()` | 不要 | なし | ❌ UIA要素なし |
| 2 | `LegacyIAccessiblePattern.SetValue()` | 不要 | なし | ❌ UIA要素なし |
| 2' | `IAccessible::put_accValue` | 不要 | なし | ❌ `E_FAIL` |
| 2'' | `IAccessibleEditableText` | 不要 | なし | ❌ IA2非公開 |
| **3** | **`PostMessage(WM_CHAR)` を FLUTTERVIEW へ** | **不要** | **なし** | ✅ **実機確認済み。これが本命** |
| 4 | クリップボード + Ctrl+V | 残る | なし | 未検証（不要） |
| 5 | 現状の `SendKeys` | 残る | あり | — |

作業順序も、当初の想定から次のように変わる。

1. `Aiv2EditorElem` を **UIA から MSAA へ全面的に書き換える**
   （2.14系ではUIA経路が成立しないため、2.14系向けに作り直す。
   旧バージョン向けの経路は手元に検証環境が無いので、
   代わりに「画面を認識できない」旨をログに出す形にした）
2. テキスト投入を `PostMessage(WM_CHAR)`、消去を `VK_BACK` + `VK_DELETE` に置換し、
   `SetForegroundWindow` / `SendKeys` を全廃 → **`/play` はフォーカス奪取ゼロになる**
3. `SanitizeText()` を縮小:
   - 1段目（`{}~+^%\r\n"()` 削除）→ **撤廃**。SendKeys固有の都合だった
   - `、` の置換 → **撤廃**。読点は文を分割しないので問題なし
   - `。？！` → 既定はカンマ置換のまま維持（Editor仕様のため必要）。
     加えて「句読点を保って1文ずつ再生」モードを設定で選べるようにする
4. ボタン操作を `accDoDefaultAction` に置換。書き出しダイアログのみ別扱い（§7）
   → 実装フェーズで **UIA 併用はやめ、Win32 のコントロールID**に変更した。§11.4 が最終形
5. 要素特定を index ではなく role+name ベースに（キャッシュ化も併せて）
6. スピンウェイトの修正・例外処理の見直し・`Thread.Abort` 置換（当初の P1/P2 のまま有効）
   - なお「UIA総当たりが重い」という当初の懸念は、MSAAツリーが83要素・全走査で約300msと
     軽いため優先度が下がる。ただし100msポーリングで回すには依然重いので、間隔調整は必要
     （実装フェーズで再計測 → **107ms**。それでも100msポーリングには重い。§11.2）
7. プリセット切替は、ブロックへのキャラクター割り当て経路を特定してから

**なお、A.I.VOICE1 経路（公式API使用）は今回の調査対象外で、実機での回帰試験は行っていない。**
クリップボード監視ループ・`WriteLog()`・`Window_Closing` は両エンジンで共有しているため、
「触っていないから影響が無い」とは言えない。未検証として扱うこと。

## 11. 実装フェーズで判明した事項（追記）

§1〜§10 は調査フェーズ（読み取り中心）の結果。以下は `Aiv2EditorElem` を MSAA 版へ
書き換えて実機に当てる過程で新たに分かったこと。**いずれも実装上必須の知見**。

### 11.1 文の区切り文字は `。｡？?！!` の6文字ちょうど

§6 では全角の `。？！` しか確認していなかった。半角・類似記号を含めて総当たりし直した結果:

| 文字 | 分割 |
|---|---|
| `。` `｡` `？` `?` `！` `!` | **する** |
| `、` `､` `．` `.` 改行 | しない |

検証手順: テキストを投入 → `次の文` を押す → MSAAツリーのアクセント表示を差分比較。
アクセント表示が変わらなければ分割されていない。

→ 実装の `Aiv2EditorElem.SentenceTerminators` / `CountSentences()` はこの6文字で判定する。
`SanitizeText()` のカンマ置換対象も同じ6文字に揃えた（`、` `．` は置換しない）。

### 11.2 MSAAツリー全走査は 107ms — キャッシュが必須

`Aiv2Native.Dump(hwnd, 40)` の実測が **107ms**（83要素時）。
クリップボード監視スレッドは 100ms 間隔で `IsEnabledPlay()` を呼ぶため、
毎回走査すると CPU 使用率が跳ね上がる。

→ `RefreshCache()` で**1回の走査から再生/書き出し/前の文/次の文/セリフ欄の
`IAccessible` を全部拾ってキャッシュ**する構造にした。

**キャッシュした `IAccessible` の参照は UI 変化をまたいでも有効**（stale にならない）ことを
別途確認済み: `次の文` を押した後も同じノード参照に対する `accDoDefaultAction` が `S_OK` を返す。
無効化が必要なのは Editor のプロセスが変わったときだけ（`Reset()`）。

### 11.3 `前の文` / `次の文` の直後には settle 待ちが要る

`次の文` の `accDoDefaultAction` が `S_OK` を返した直後に `再生` を押すと、
**再生が始まらないことがある**。`PlayAllSentences` が 3.13 秒で false を返す症状として出た。

当初はノードが stale になったと疑ったが、プローブで否定された（11.2 参照）。
1手ずつ 200ms 空けて手動でなぞると 3文が正常に再生される（10.13s）ことから、
**Editor 側が文の切り替えを反映し終える前に再生要求が飛んでいた**と確定。

→ `InvokeNextSentence()` / `InvokePrevSentence()` の成功後に
`SentenceSettleMs = 200` の固定待ちを入れた。

### 11.4 書き出しダイアログはネイティブのコントロールIDで引く

§7 の UIA 経路は**採用しなかった**（`AutomationId="1"` がファイル一覧の ListItem とも
衝突して一意に決まらない）。共通ダイアログのコントロールIDはロケールにも
Windows バージョンにも依存しないので、そちらを使う。

| 対象 | 取得方法 |
|---|---|
| 保存ボタン | `GetDlgItem(dlg, 1)` … IDOK（表示は `保存(&S)`） |
| キャンセル | `GetDlgItem(dlg, 2)` … IDCANCEL |
| ファイル名欄 | ctrl id **1001** の `Edit`。ただし **`GetDlgItem(dlg, 1001)` は NULL を返す** |

ファイル名欄は `ComboBoxEx32` > `ComboBox` > `Edit` という**孫**なので、
`GetDlgItem` の直接の子検索では見つからない。
→ `Aiv2Native.FindDescendantByCtrlId(dlg, 1001, "Edit")` で再帰的に探す。

押下は `PostMessage(IDOK, BM_CLICK)`。**フォーカスを当てなくても効く**ことを実機で確認。
ファイル名の読み取りは `WM_GETTEXT`（`SendMessageTimeoutW`）。
Editor が入れてくる既定名は `0_<セリフ先頭>.wav` の形式。

> ダイアログ自体が前面に出るのは Editor 側の挙動で回避できない（§7 のまま）。
> ただし `SaveAudioAiv2()` は**開く前の前面ウィンドウを退避し、完了後に復帰させる**ようにした。

### 11.5 【重要】文の位置を戻さずにテキストを差し替えないこと

Editor は「現在どの文を選んでいるか」を**テキストを差し替えても保持する**。
そのため、文ごと再生で位置を進めたまま、より短いテキストに差し替えて再生すると、
Editor 側で範囲外アクセスが起きて画面がエラー表示に切り替わってしまう。
こうなると MSAA ツリーも崩れ、以降は自動操作を受け付けなくなる。

（外部からの自動操作でしか作れない状態であり、Editor を手で使っている限りは起きない。
具体的な操作手順はここには書かない。）

→ **「テキストを差し替える前に先頭の文へ戻す」を実装した。**
`Aiv2EditorElem.SetText()` の先頭で `RewindToFirstSentence()` を呼ぶ。
位置は変数で覚えない（理由と限界は §17・§18 を参照）。
文ごと再生を使うかどうかに関わらず、この手順は守ること。

回帰テストケース: 3文を文ごと再生 → 1文のテキストに差し替え → 再生。
修正後は正常（1.68s、Editor健在）。

#### 修正前のクラッシュを意図的に再現した（2026-08-01 追試）

それまでは「修正後に落ちないこと」しか実測しておらず、
「修正しなければ落ちること」は個別実測からの推論だった。製品コードは変更せず、
`Aiv2EditorElem` の公開メソッドと `Aiv2Native.PostText` で修正前の手順を組んで再現した。

| 位置の進め方 | 差し替え | 差し替え〜再生の間に MSAA 走査 | 結果 |
|---|---|---|---|
| `次の文` ×29（index 29） | 巻き戻さず1文へ | あり | 落ちない |
| `次の文` ×29（index 29） | 巻き戻さず1文へ | **なし** | **クラッシュ** |
| 文ごと再生 ×3（index 2） | 巻き戻さず1文へ | あり | 落ちない |
| 文ごと再生 ×3（index 2） | 巻き戻さず1文へ | **なし** | **クラッシュ** |
| 文ごと再生 ×3 → 利用者が入力欄を空に | 巻き戻し0回で1文へ（§17.4） | なし | **クラッシュ** |
| 文ごと再生 ×3 → 利用者が入力欄を空に | **修正後の `SetText()`** | なし | 健在・2,618ms |
| `次の文` ×29 → 利用者が入力欄を空に | **修正後の `SetText()`** | なし | 健在・2,777ms |

崩壊したツリー（12要素）から読めたエラーは記録どおりのものだった:

```
RangeError (length): Invalid value: Only valid value is 0: 2
```

**分かったこと2点:**

1. **`次の文` で進めただけでも落ちる。** 実際に再生して進める必要はない
2. **差し替えと再生の間に MSAA 走査（107ms）を1回挟むと再現しなくなる。**
   §18 の表示崩れと同じマスキング。最初の2回が「落ちない」と出たのは
   プローブ自身が観測のために走査していたせいだった。
   **観測が結果を変えるので、この種の再現試験では走査を挟まないこと**

なお崩壊した Editor の `GetAvailability()` は `ElementsNotFound` を返す。
起動直後（§16）と同じ値なので、これだけでは区別できない。

#### エラー表示になった Editor の閉じ方

この状態の Editor は `終了` への `accDoDefaultAction` に反応しない
（`INVOKE_OK` は返る）。`WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / `WM_LBUTTONUP` を
`FLUTTERVIEW` へ `PostMessage` すれば閉じられる。座標は MSAA の `accLocation` から取り、
`ScreenToClient` でクライアント座標へ変換して lParam に入れる。
**合成マウスメッセージはフォアグラウンドを奪わずに FLUTTERVIEW へ届く。**

### 11.6 ボタン押下は稀に取りこぼされる → 1回リトライする

`accDoDefaultAction` が `S_OK` を返したのに Editor が反応しないケースを
`書き出し`（ダイアログが出ない）で1度観測した。再送で成功。

→ `StartPlay(timeoutMs)` / `StartWrite(timeoutMs)` を用意し、
**1回目の待ち時間を短く（書き出しは4000ms）打ち切って押し直す**構造にした。

### 11.7 再生ボタンが消えている状態を待ち続けない

`WaitUntilIdle()` が 120 秒スピンし続ける事故が起きた（11.5 の状態では
再生ボタンごと消えているため、「再生中でない」と判定し続けてしまう）。

→ 再生ボタンの状態を `Missing` / `Idle` / `Busy` の3値で表し、
**`Missing` が3回連続したら異常とみなして待機を打ち切る**。

### 11.8 PotatoVoiceHub 本体は管理者権限で動く（自動UI検証は不可）

`app.manifest` が `requireAdministrator`。したがって非昇格プロセスからは UIPI により

- `PostMessage(WM_CLOSE)` が無視される
- UIA でツリーを読むと descendants = 0
- 合成マウス入力が届かない
- `Stop-Process` がアクセス拒否

いずれも**アプリ側の不具合ではない**。本体GUIの自動検証をしたい場合は
検証スクリプト側も昇格させること。

### 11.9 検証スクリプトを書くときの環境上の注意

| 事象 | 対処 |
|---|---|
| PowerShell 7 は net472 の WPF アセンブリをロードできない | `powershell.exe`（5.1）で実行する |
| `Add-Type -Path` は `.EXE` を拒否する | `[Reflection.Assembly]::LoadFrom($exe)` |
| PS 5.1 が日本語スクリプトを文字化けさせる | **UTF-8 BOM 付き**で保存する |

## 12. プリセット（キャラクター）切り替え — 経路を特定・実装済み

A.I.VOICE 1.x の `TtsControl.VoicePresetNames` / `CurrentVoicePresetName` に相当する操作。
2.14.1 では「テキストブロックに割り当てるキャラクター」を変える操作がそれにあたる。

### 12.1 唯一の経路はメニューの3段たどり

```
メニュー[キャラクター] → [テキストブロックに割り当て] → [N番目のキャラクター]
```

- **`テキストブロックに割り当て` はアクションではなくサブメニュー。**
  押すと要素数 89→102 に増え、その中に項目が現れる。
  最初これをアクションだと思って押し、「INVOKE_OK なのに何も起きない」と誤読した。
- サブメニューの項目は次の11個。**`N番目` は左のキャラクター一覧の並び順に対応する**（実機で確認）。

| 項目 | ショートカット |
|---|---|
| 選択中のキャラクター | Ctrl+Q |
| 1番目のキャラクター | Ctrl+1 |
| …（2〜9番目） | Ctrl+2 〜 Ctrl+9 |
| 10番目のキャラクター | Ctrl+0 |

- 3段とも `accDoDefaultAction` で通り、**フォアグラウンドは奪わない**。
- 反映されるとブロック行のグラフィックの name と右パネルの name が同時に変わる。

### 12.2 ショートカットは PostMessage では効かない（重要）

`Ctrl+1`〜`Ctrl+0` を `PostMessage(WM_KEYDOWN/WM_KEYUP)` で送っても**何も起きない**（実機で確認）。
投げたメッセージではスレッドの修飾キー状態が更新されないため、Editor 側は Ctrl が
押されていないものとして扱う。テキスト投入の `WM_CHAR` が通るのとは事情が違う。
→ **修飾キーを伴う操作は諦めてメニューをたどること。**

### 12.3 一覧の読み取り方

左の一覧の各行は `role=グループ化(20)` / `name="キャラクターチューニング"`。
その**直後**に来る `role=グラフィック(40)` が表示名で、`"キャラクター名\nプリセット名"`。
`Dump` は先行順なので「グループを見つけたら次のグラフィック」で拾える。

現在の割り当ては、**セリフ入力欄（`role=42` かつ name 空）の直前のグラフィック**の name。
これがブロック行の親にあたる。

**`SELECTED` 状態はどのノードにも立たない。** 一覧のどの行が選択中かは MSAA からは読めない。
そのため「選択中のキャラクター」を使う経路は状態を確認できず、`N番目` の方が確実。

### 12.4 実装（`Aiv2EditorElem`）

| API | 内容 |
|---|---|
| `GetVoicePresetNames()` | 一覧を上から `"キャラ名 / プリセット名"` で返す |
| `GetCurrentVoicePresetName()` | 今ブロックに割り当たっているキャラクター名 |
| `SetVoicePreset(name)` | 切り替え。名前は全体・キャラ名のみ・空白なしのどれでも可 |

- `/play?preset=` `/saveAudio?preset=` から呼ばれる（`MainWindow.xaml.cs` の `SetPresetAiv2`）。
- メニュー各段のあとに **400ms の settle** が要る。`accDoDefaultAction` が S_OK を返した
  直後はまだツリーに項目が現れていない。
- **既に割り当たっている場合は何もせず true を返す。**
  3段たどると実測 1.8〜2.4秒かかる。棒読みちゃんは1行ごとに preset を送ってくるので、
  この早期リターンがないと毎行2秒待たされる（同名指定時は実測 241ms）。
- 途中で失敗したらメニューが開きっぱなしになり以降の操作を全部食われるので、
  `VK_ESCAPE` を3回送って必ず閉じる。
- **11番目以降は切り替えられない。** メニューに項目がないため。

### 12.5 実機での動作確認（Editor 2.14.1、フォアグラウンド不変）

```
一覧 (4件): 紲星あかり(NV) / 標準 | 紲星 あかり / 標準 | 紲星 あかり（蕾） / 標準 | 紲星 あかり（萌） / 標準

SetVoicePreset('紲星あかり(NV) / 標準')  = True  (2440ms) -> 現在=[紲星あかり(NV)]

## 13. `/saveAudio` の `path` を反映するようにした — 実機確認済み

### 13.1 症状

`/saveAudio?text=...&path=D:\temp\test.wav` を投げると HTTP は `{"status":"ok"}` を返すが、
指定した場所にファイルができない。

### 13.2 原因

`MainWindow.xaml.cs` の `/saveAudio` ハンドラが `queryString["path"]` を読んでおらず、
`SaveAudioAiv2(text)` にテキストしか渡していなかった。書き出しダイアログは既定の
ファイル名（`0_書き出しのテストです… .wav`）のまま `保存` されるため、Editor が最後に
使ったフォルダへ既定の名前で保存される。

この点は upstream `f3ba895` の時点から同じで、今回の変更で入った回帰ではない。

### 13.3 修正

`path` をハンドラから通し、共通ダイアログのファイル名欄（ctrl id **1001** の `Edit`）へ
`WM_SETTEXT` で書き込む。フルパスを入れれば共通ダイアログ側が解決するので、
フォルダを開き直す操作は要らない。

- 書き込み後に `WM_GETTEXT` で読み戻して一致を確認する。
- 書き込めなかった場合は**保存せずキャンセルする**。
  既定のファイル名のまま `保存` すると意図しない場所に書き出されてしまうため。
- 親フォルダは事前に `Directory.CreateDirectory` で作る。

クリップボード経由の書き出しも同じ経路に載せ、`option.saveAudioPath` の
`{yyyyMMdd}` `{HHmmss}` `{VoicePreset}` `{Text}` を展開して渡すようにした
（`{VoicePreset}` は `GetCurrentVoicePresetName()` から取る）。

### 13.4 実機確認（Editor 2.14.1）

```
テキスト投入 OK
ダイアログ = 8263672
既定のファイル名 = [0_書き出しのテストです… .wav]
SetSaveDialogFileName = True
書き込み後      = [D:\temp\test.wav]
AcceptSaveDialog = True
生成された: D:\temp\test.wav  204750 bytes
```

なお共通ダイアログは表示時にフォアグラウンドを奪う（Editor 側の挙動で制御不可）。
`/saveAudio` だけは前面が入れ替わる。

**この時点では「ダイアログが閉じた＝書き出しが終わった」と思っていたが、これは誤り。**
実際にはそこから約1.8秒かかる。§15 を参照。

### 13.5 `/saveAudio` のクエリ文字列は `saveAudioEncode` で復号される（利用者向けの落とし穴）

`/play` はクエリを既定（UTF-8）で復号するが、`/saveAudio` は
`HttpUtility.ParseQueryString(query, option.saveAudioEncode)` で復号する。
`saveAudioEncode` の既定は Shift-JIS 系なので、UTF-8 でパーセントエンコードした
クエリを投げると Editor 側で文字化けする。

```
[uri]::EscapeDataString('テスト。')  →  Editor には 繝・せ繝医・ が入る
```

対処はどちらか:

- 共通設定タブの `saveAudioEncode` を `utf-8` にする（`/play` と揃う）
- クエリを Shift-JIS でエンコードして投げる

### 13.6 同名ファイルへの上書き確認は TaskDialog — `BM_CLICK` で押す

保存先に同名ファイルがあると、共通ダイアログが `名前を付けて保存の確認`
（`test.wav は既に存在します。上書きしますか?`）を挟んで止まる。

このダイアログの構造:

- クラスは `#32770`、**owner が書き出しダイアログ**（`GetWindow(h, GW_OWNER)` で引ける）
- 中身は TaskDialog。`DirectUIHWND` / `CtrlNotifySink` の下に
  **実 HWND のボタン**（class `Button`、`はい(&Y)` / `いいえ(&N)`）がある
- ただし **`GetDlgCtrlID` が 0 を返す**ので `GetDlgItem(h, IDYES)` では取れない
- **`WM_COMMAND(IDYES)` は効かない**（実機確認済み）
- **`TDM_CLICK_BUTTON`(WM_USER+102) も効かなかった**
- **`PostMessage(BM_CLICK)` を `Button` の HWND へ直接投げると押せる**

実装 `Aiv2EditorElem.ConfirmOverwrite` は、`Button` クラスの子孫を列挙して
先頭（=`はい`）へ `BM_CLICK` する。TaskDialog のボタンは `[はい][いいえ]` の順に
作られるので先頭が `はい`。**ボタンがちょうど2つでなければ何も押さない**。

正規の `TDM_CLICK_BUTTON` を先に試す実装も書いてみたが、この確認ダイアログには
効かないことが実機で分かったので消した。効かない経路を残しておくと、
「ボタンが2つでないので押さなかった」ケースでも
`TDM_CLICK_BUTTON` だけが飛んでしまい、ガードの意味がなくなる。

**ただしボタンが2つというだけでは、それが上書き確認である証明にはならない。**
そこで肯定するかどうかは呼び出し側が決める。`SaveAudioAiv2()` は保存を確定する前に
ファイル名欄の絶対パスが実在するかを確かめ、上書きになると分かっているときだけ
`AcceptSaveDialog(dialog, timeout, allowOverwrite: true)` を渡す。
`allowOverwrite` が false のまま確認が出た場合は、何のダイアログか分からないものとして
`WM_CLOSE`（TaskDialog では否定＝キャンセル）で閉じ、書き出しごと失敗させる。

これでも「既存ファイルを指定したときに出た2ボタンダイアログ」が
上書き確認以外である可能性は残る（拡張子・アクセス権・ネットワーク先の警告など）。
ロケール非依存な識別子が無いため種類の判定はしておらず、
**誤爆の範囲を「上書きになると分かっている場合」に狭めただけ**である。

`AcceptSaveDialog` は保存ダイアログが閉じるまでのポーリング中に
この確認を探し、`allowOverwrite` なら押す。押下は取りこぼされうるので、
閉じるまで毎周回試す（自然にリトライになる）。

実機確認（Editor 2.14.1）:

```
1回目(新規)  : Accept=True 317ms  存在=True 203474bytes  更新された=True
2回目(同名)  : Accept=True 873ms  存在=True 203474bytes  更新された=True
3回目(同名)  : Accept=True 664ms  存在=True 203474bytes  更新された=True
```

**この数字は「ダイアログが閉じるまで」であって、書き出しの完了までではない。**
`存在=True` になっているのは、直前の周回で書かれた古いファイルを見ているため。
書き出し完了待ちを入れたあとの実測は 3.0s / 2.6s / 2.4s（§15.4）。

なお `AcceptSaveDialog` が失敗した場合は `CancelSaveDialog` で畳む。

## 15. 書き出しは非同期 — ダイアログが閉じても終わっていない（2026-07-31 追試）

### 15.1 症状

`path` を指定した書き出しを3回連続で実行したところ、**2回目が
「書き出しダイアログが表示されなかった」で失敗**した。
1回目・3回目は成功し、ファイルも正しく出来ている。

さらに、1回目の直後に `Test-Path` で確認するとファイルがまだ無い。
検証を終えたあとで見ると存在していた。

### 15.2 原因 — 書き出し中はMSAAツリーが8要素まで縮む

保存ダイアログが閉じてからの Editor の状態を 250ms 間隔で追った（Editor 2.14.1）:

```
経過ms   要素数   再生ボタン        書き出しボタン     ファイル
603      8       (無し)           (無し)           -
931      8       (無し)           (無し)           -
1478     8       (無し)           (無し)           -
2023     8       (無し)           (無し)           -
2847     138     再生/0x300000    書き出し/0x300000  297276
```

- **書き出し中、Editor は進捗表示に切り替わり、MSAAツリーが 8要素まで縮む。**
  再生ボタンも書き出しボタンも1つも見えなくなる。
- 復帰までは実測で **約2.3秒**。ファイルが現れるのはダイアログが閉じてから **約1.8秒後**、
  サイズが確定するのが **約2.4秒後**。

これで2回目が失敗した理由が説明できる。1回目の書き出しがまだ走っている間に
`書き出し` ボタンを引き当てようとして、ツリーに無いので `InvokeWrite()` が false を返し、
`StartWrite()` がダイアログを待たずに諦めていた（実測 444ms で復帰）。

### 15.3 【重要】閉じた直後の `IsEnabledPlay()` は当てにならない

```
SetName=True Accept=True  ダイアログが閉じた: 2883ms
閉じた直後 IsEnabledPlay: True        ← まだ進捗表示が出ていない
書き出し中に Busy を観測 : True        ← そのあとで Busy になる
```

**進捗表示が出るまでに遅れがある**ため、ダイアログが閉じた瞬間に状態を見ると
「空いている」と読めてしまう。ここで次の要求を通すと 15.2 の失敗になる。

### 15.4 対処

`Aiv2EditorElem.WaitUntilWriteFinished(graceMs, timeoutMs)` を追加し、
`SaveAudioAiv2()` が `AcceptSaveDialog()` のあとに呼ぶようにした。

1. まず進捗表示が出る（＝再生ボタンが `Missing` になる）のを `graceMs` まで待つ
2. 出たら、`Idle` に戻るまで `timeoutMs` まで待つ

ボタンが1つも見えない状態は **Editor がエラー画面に崩れたときと区別がつかない**ので、
1段目は時間で区切り、出ないまま過ぎたら「もう終わっている」とみなす。
実装では grace=2000ms（実測は600ms以内に出る）、timeout=60000ms。

この待ちを入れたあとの実測（Editor 2.14.1）:

```
同名上書き 3連続 : 3036ms / 2564ms / 2404ms   いずれも 220,752 bytes
存在しないフォルダを指定 : 2050ms（フォルダごと作成される）
path 未指定（Editorの命名規則） : 2472ms
書き出し直後の読み上げ : OK
```

### 15.5 §11.7 との関係

`Missing` を「Editor が落ちた」とだけ解釈してはいけない、ということでもある。
**正常な書き出し中にも `Missing` は出る。**
`WaitForPlayButton` は `Missing` が3回続くと打ち切るが、これは再生の待ちに使うもので、
書き出し中に呼ばれることはない。書き出し完了待ちは上記の専用の待ちを使う。

## 17. 「現在の文」の位置は MSAA からは読めない（2026-07-31 追試）

§11.6 のクラッシュ（`RangeError`）を避けるには「テキストを差し替える前に必ず先頭の文へ戻す」
必要がある。当初の実装は**戻した回数を自分で数えて記憶する**方式だったが、これでは足りない。

- `accDoDefaultAction` は S_OK を返しても稀に空振りする（§11.9）。
  文数ぶんちょうど押すだけでは、1回でも空振りすると先頭に着かないまま「着いた」ことになる
- Editor の「現在の文」は**ユーザーがセリフ入力欄をクリックしても動く**。
  こちらの操作だけを数えていても実際の位置とはずれる

### 17.1 境界に着いたことは状態からは分からない

そこで「先頭に着いたか」を読み取れないか調べたが、**読み取れない**。
3文のテキストで `次の文` / `前の文` を押しながら、その2つのボタンと `再生` の
`get_accState` を追ったところ、**どの位置でも `0x300000` のまま変化しなかった**。

| 位置 | 要素数 | 再生 | 前の文 | 次の文 |
|---|---|---|---|---|
| 先頭（index 0） | 94 | 0x300000 | 0x300000 | 0x300000 |
| index 1 | 94 | 0x300000 | 0x300000 | 0x300000 |
| index 2（末尾） | 94 | 0x300000 | 0x300000 | 0x300000 |
| 末尾で更に `次の文` | 94 | 0x300000 | 0x300000 | 0x300000 |
| 先頭で更に `前の文` ×2 | 94 | 0x300000 | 0x300000 | 0x300000 |

`STATE_SYSTEM_UNAVAILABLE`(0x1) は**どちらのボタンにも立たない**。
端に着いてもボタンは無効化されず、押しても何も起きないだけ。
要素数も変わらないので、ツリーの形からも判別できない。

→ **境界を観測する方法は無い。** 位置を確実にするには「押した回数」に頼るしかない。

### 17.2 対処 — 覚えずに毎回、多めに押す

- 位置は記憶しない。`SetText()` の直前に毎回押し直す。
  ユーザーの操作でずれても、差し替え直前に押すので影響を受けない
- 文数ぶんの倍（最低でも +2 回）押す。
  先頭で `前の文` を押しても何も起きない（上表）ので、多めに押す側は安全
- テキストが1文なら「現在の文」は先頭以外になりえないので、1回も押さない。
  句読点をカンマへ置換する既定の動作では常にこちらになり、追加コストはゼロ
- `PlayAllSentences()` の末尾では戻さない。次の `SetText()` が必ず戻すので不要

### 17.3 【重要】これは保証ではない

余分に押すぶんは**実測に基づく安全マージンであって、保証ではない**。
押した結果を読み取る手段が無い（17.1）以上、必要な回数ぶん成功しなければ
先頭に着かないまま成功として扱われる。文数 `N` に対して `2(N-1)` 回押すので、
3文以上なら**半分を超えて**空振りした場合。2文なら最低 +2 回が効いて3回押すので、
**3回とも**空振りした場合になる。
比例させているので許容できる空振り率は文数によらず一定になる（固定で +2 回にすると、
文数が増えるほど「3回空振りすれば破れる」側に寄っていく）。

**残っているリスク**: この安全マージンを破ると §11.5 の `RangeError` が起きうる。

`Aiv2EditorElem.RewindMaxPresses`（1000回）を超える場合は押さずに失敗させる。
既存テキストが500文を超えているときだけ当たる。要求全体が
何分もブロックされるのを防ぐためで、成功させるためのものではない。

### 17.4 一度範囲外になった位置は戻せない

「先に消してから戻す」ができないことを実機で確認した。
末尾（index 2）で**セリフ入力欄を空にしてから** `前の文` を1回・3回押し、
同じ3文を打ち直して再生したところ、いずれも**3文目が再生された**
（1文目 1.37s / 3文目 4.90s で区別）。

- 空にしても「現在の文」の位置は保持される
- **その状態で `前の文` を押しても位置は動かない**。
  文が1つしかないテキストでは `前の文` は何もしないため

→ 巻き戻しは**必ずテキストを差し替える前**に行う必要がある。
差し替えた後で気づいても復旧できない。

**入力欄が外から空にされた場合も同じ穴になる。** 空のテキストは1文と数えられるので、
そのまま差し替えると「1文だから巻き戻し不要」と判断してしまい、
末尾に残った位置のまま文数の少ないテキストへ差し替えることになる。
表示崩れ（§18）の復旧手順として利用者に入力欄を空にしてもらう以上、これは現実に起きる。

→ `Aiv2EditorElem.RestoreSentencesForRewind()` で塞いだ。判定はひとつだけ:

**入力欄の中身がこちらの入れたものと一致するか。**

- **一致する**: 位置はその文数を超えない（こちらが入れて、こちらが再生したので）。
  そのまま巻き戻せる。**通常はこちら**で、追加コストはゼロ
- **一致しない**: 外から書き換えられている（か、接続後まだ一度も入れていない）。
  このとき**位置に上限を置けない**。利用者は文を増やしてから消すこともできるので、
  今の文数からも、こちらが最後に入れたテキストの文数からも「これだけあれば足りる」
  とは言えない。**100文の足場を敷いてから巻き戻す**

足場は `RewindScaffoldSentences`（100）ぶんの `あ。`。
「前の文」はこれだけの文があれば、そこより手前のどの位置からでも先頭へ戻せる。

覚えるのは**テキストであって位置ではない**（位置を覚えてはいけない理由は §17.1）。
`Reset()` で `lastSetText` を見失っても足場の側へ倒れるので、
余分に時間がかかるだけで判断を誤ることはない。

実機確認（いずれも**クラッシュせず再生でき、ツリーは98要素で健在**）:

| 経路 | 実測 |
|---|---|
| 30文の末尾で手動クリア → 別インスタンスが1文へ差し替え（＝アプリ再起動相当） | 2,087ms |
| こちらは1文しか知らないのに、外から30文へ書き換えて末尾へ進め、手動クリア | 1,830ms |
| 外から3文へ書き換えられた直後 | 1,990ms（次の要求からは148ms） |
| 外から触られていない通常の差し替え | 151 / 378 / 475 / 725ms（既存 1 / 3 / 10 / 30文） |

#### 残る穴（承知のうえで受け入れているもの）

**(1) 位置が100文目より後ろから始まっていた場合は戻せない。**
足場をいくつ敷けば足りるかは位置が読めない以上わからない。

**(2) 一致は「その間に外から触られていない」ことの証明ではない。**
文を増やして位置を進めたあと、**元と同じ文字列へ戻される**と素通りする。
実際に踏むには、要求と要求の間に次を全部やる必要がある:

1. 入力欄を2文以上に増やす
2. 現在の文を先頭以外へ動かす
3. **こちらが最後に入れた文字列へ1文字違わず戻す**（現実的には Ctrl+Z）
4. その状態で次の要求が来る

これを塞ぐには**毎回足場を敷く**しかないが、1回あたり約2秒かかる。
棒読みちゃんは1行ごとに要求を送ってくるので、常時2秒は載せられない。

**足場なしで「多めに押す」では代用できない。** §17.4 のとおり、
文が1つしかないテキストでは `前の文` は位置を動かさない。
位置が動くのは入力欄に十分な文がある間だけなので、
足場を敷くことと押すことは切り離せない。

どちらも踏むと §11.5 の `RangeError` になる。復旧は Editor の再起動。

### 17.5 `前の文` / `次の文` の 200ms 待ちは連打には要らない

§11.7 の「移動の直後は200ms待つ」は、**移動してから `再生` を押すまで**に必要な待ちで、
移動を続けている間は要らない。30文のテキストで末尾から `前の文` を60回、
間隔を 200 / 100 / 50 / 20 / 0 ms と変えて押したが、**どれも先頭に着いた**
（0ms で 475ms、200ms で 12,604ms）。5連打の精密試験でも取りこぼしゼロ。

→ 巻き戻しは間隔を空けずに押し、**最後に1回だけ** 200ms 待つ。
これで「倍押す」ようにしても実測は従来より速い。

| 既存テキスト | 差し替えにかかる時間（巻き戻し込み） |
|---|---|
| 1文 | 154ms |
| 3文 | 398ms |
| 10文 | 522ms |
| 30文 | 862ms |

  つまり**ロックは発話全体のあいだ握られたまま**
- 監視ループの busy 判定もロックを取る（同 `:450`）ので、読み上げ中の監視スレッドは
  そこでブロックして止まっている。**文と文の切れ目には割り込めない**（切り分け2で
  `2busy=False` が一瞬見えるが、それは外部から MSAA を直接読んでいるため）
- `aiv2KeepPunctuation=False`（既定）では `StartPlay` が再生開始で返る（同 `:849`）。
  **ハンドラは Editor が喋っている最中にロックを離す**
- HTTP リクエスト同士は競合しない。`startLoop` が次の `BeginGetContext` を仕掛けるのは
  現在の要求を処理し終えたあと（同 `:151-152`）。競合は常に「監視スレッド 対 HTTP」

**取りこぼしが成立する条件**は「外側の busy 判定（`:450`）では idle、
内側の再判定（`:514`）では busy」。監視ループは2つの lock の**間でロックを離している**
（クリップボード読み取りと 1.x 処理はロック外）ので、その隙間に HTTP が入れる。

```
lock { isAiv2Busy = !IsEnabledPlay(); }   :450  ← idle だった／ロックを離す
GetClipboardTextSafe()                    :462  ┐ この間ロックは空
_ttsControlAiv1.Text = text; Play();      :499  ┘ HTTP が lock を取れる
lock { if (IsEnabledPlay()) ... }         :510  ← busy に見える
```

`False` のときはこれが普通に起こりえる。`True` のときは `PlayAllSentences` が
タイムアウト等で途中復帰した場合のみ。ただし 3-4 では **1.x も喋っていない**。
1.x 側の失敗は `catch { }` に落ちて痕跡が残らないため、そこは特定できなかった。

### 19.2 `aiv2Sync` を広げても直らない

ロックは**本アプリのスレッド同士**の交通整理であって、Editor を占有できるわけではない。
利用者が Editor で手で再生を押せば、ロックが空いていても Editor は喋っている。
`IsEnabledPlay()`（MSAA で再生ボタンの `再生`/`停止` を読む）だけが実際の発話状態。
したがってループ本体を丸ごと囲っても、内側で busy を見る状況は消えず、
**「延期するか既読にするか」の判断は残る**。

囲うこと自体の副作用も2つある。

- ループ本体には 1.x の `SaveAudioToFile`（`:490`）が入る。完了までブロックするので、
  2 と無関係な書き出しが終わるまで `/play` が待たされる
- `GetClipboardTextSafe()`（`:462`）の中身は `Dispatcher.Invoke`。
  **`aiv2Sync` を持ったまま UI スレッドを待つ**ことになる。
  このパターン自体は既にある（`ReportAiv2State()` → `WriteLog()` → `Dispatcher.Invoke`、
  `:559-563` を `:270` `:452` から呼ぶ）。今それが安全なのは
  **UI スレッド側が `aiv2Sync` を取る経路が1本も無い**からで（`aiv2Sync` の出現は
  宣言含め `:34` `:268` `:450` `:510` の4箇所だけ）、広げるとデッドロックの面積が増える

### 19.3 根本は「保留中の仕事を置く場所が無い」こと

既読の記録が `clipboardTextLast` 1本しかなく、「1.x は済んだが 2 はまだ」を表現できない。
2 が busy のとき監視ループの選択肢は2つしかない。

- 既読にしない → 100ms 後の周回で同じテキストがまた未読で通り、**1.x が二度読み上げる**
- 既読にする → **2 が取りこぼす**

`isAiv2Deferred = _ttsControlAiv1 == null`（`:534`）はこの二択で、
1.x が接続されていれば後者を選ぶ。**upstream (`f3ba895`) は無条件に既読**にしていた
（busy 判定も再確認も無く、busy でも `PlayAiv2` を呼んで走っている発話を上書きしていた）ので、
**1.x 併用時の既読の付け方はこのブランチでも変わっていない**。退行ではない。

Editor を1本のスレッドが専有してキューを順に処理する形にすれば、**積んだ時点で既読にできる**
ので取りこぼしも二度読みも消える。エンジンごとの状態もキューを2本にするだけで済む。
ただし `/play` が `ok` / `busy` を同期で返す今の API 契約が変わる。

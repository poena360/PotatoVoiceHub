# A.I.VOICE2 の操作を MSAA 経由に置き換え、フォアグラウンド奪取をなくす

## はじめに

A.I.VOICE2 に公式APIが無い中で、ここまで動くものを作って公開してくださっていることに感謝しています。
棒読みちゃんの音声を A.I.VOICE2 に差し替えたくて使わせていただいたのですが、
手元の A.I.VOICE2 Editor **2.14.1** では読み上げまで進まなかったため、原因を調べて手を入れました。

**先にお伝えしておきたいこと**

- 実装は AI エージェント（Claude）を使って行いました。
  AI が書いたコードをそのまま取り込むのに抵抗がある場合は、**調査結果だけでも参考にしていただければと思います。** そのために調べたことは全部書き出してあります。
  問題無ければこちら側からPRを作成させて頂くことも可能です。
- 差分が大きく（+1,681 / -183）、A.I.VOICE2 経路はほぼ書き直しになっています。
- **A.I.VOICE1（無印）の公式API (`TtsControl`) を叩いている箇所そのものは触っていません。**
  ただしクリップボード監視・ログ・終了処理といった**両方が通る共通部分は変更している**ため、
  A.I.VOICE Editor 1.4.3 を同時起動して両方に接続した状態でも確認しました
  （詳細は「互換性について」と「検証内容」に書きました）。

Issue #2 の「A.I.VOICE2 では読み上げ中に入力のためフォーカスが持っていかれる」という件も、
私の読み違いでなければこの変更で解消されるはずです（`/play` 経路はフォアグラウンドを一切奪いません）。

---

## 何が起きていたか

A.I.VOICE2 Editor 2.14.1 は **Flutter で作られたアプリ**になっており、
`System.Windows.Automation`（UI Automation）からは要素がまったく見えません。

```
MSAA (IAccessible)               : 83 要素
UIA (System.Windows.Automation)  :  0 要素
```

現行の `Aiv2EditorElem` は UIA だけを使っているため、2.14.1 では

- `GetElemAiv2Play()` が常に `null`
- → `IsEnabledPlay()` が常に `false`
- → HTTP ハンドラの `if (!IsEnabledPlay()) → busy` により、
  `/play` `/saveAudio` `/getStatus` がいずれも `{"status":"busy"}` を返す

という状態になっていました。

このコードは 2024年3月〜2026年1月にかけて実際に調整されている（README のリリースノート）ので、
当時の Editor は UIA を公開していたのだと思います。
**Editor 側が Flutter へ移行したタイミングで UIA 経路が成立しなくなった**、
というのが素直な説明で、コードの側に問題があったわけではないと考えています。

一方、**MSAA (`IAccessible`) は使えます。**
`AccessibleObjectFromWindow` で子ウィンドウ `FLUTTERVIEW` を叩くと、
Flutter がそこで初めてセマンティクスを構築して 83 要素のツリーを返してきます。
これを土台に組み直したのが今回の変更です。

> なお IAccessible2 系（`IAccessibleEditableText` など）は `QueryService` が全て `E_FAIL` で、
> 公開されていませんでした。使えるのは MSAA だけです。
>
> 調査は公開されたアクセシビリティAPI（MSAA / UI Automation）と Win32 メッセージのみで行っており、
> 逆コンパイルやプロトコル解析は一切していません。

## 変更点

### 1. `Aiv2Native.cs`（新規） — MSAA / Win32 の薄いラッパ

`IAccessible` の COM 宣言、ツリー走査、`accDoDefaultAction`、`accSelect`、
`PostMessage` によるキー送出、共通ダイアログ操作をまとめた新規ファイルです。
外部ライブラリの追加はありません（`oleacc.dll` / `user32.dll` の P/Invoke のみ）。
csproj は SDK スタイルなので、プロジェクトファイルの変更も不要でした。

### 2. `Aiv2EditorElem.cs` — UIA から MSAA へ全面的に書き換え

| 旧 | 新 | 備考 |
|---|---|---|
| `GetElemAiv2Write2()` / `GetInvokeAiv2Write2()` | 廃止 | `書き出しを実行` という要素は 2.14.1 には無く、Windows の共通ダイアログに変わっています |
| `GetHandle()` / `SetFocusMainWindow()` | 廃止 | 前面化・フォーカス移動が不要になったため |
| `InvokeWrite1()` / `InvokeWrite2()` | `InvokeWrite()` / `StartWrite()` | |
| `InvokePlay()` | `InvokePlay()` / `StartPlay()` | |
| — | `SetText()` / `GetText()` / `ClearText()` | 新設。テキスト投入をこちらへ移動 |
| — | `SetVoicePreset()` ほか | 新設。プリセット切替 |
| — | `GetAvailability()` | 新設。後述 |

要素の特定は、走査順やインデックスではなく **role + name** で行うようにしました
（`再生` ボタンは `role=43`、セリフ入力欄は `role=42` かつ name が空、など）。
ツリー全走査は 83 要素で実測 **107ms** かかるので、
**1回の走査で必要なノードを全部拾ってキャッシュ**しています。

### 3. テキスト投入を `SendKeys` → `PostMessage(WM_CHAR)` に

ここが今回の中心です。

**旧:**
```
前面ウィンドウを退避 → SetForegroundWindow → SetFocus
→ SendKeys("^z") で前のセリフを消す
→ SendKeys(text)
→ Thread.Sleep(aiv2SendKeysSleep) の固定待ち
→ 再生ボタンを Invoke
→ 前面ウィンドウを復帰
```

**新:**
```
セリフ入力欄へ accSelect(SELFLAG_TAKEFOCUS)
→ PostMessage(FLUTTERVIEW, WM_KEYDOWN/UP, VK_BACK + VK_DELETE) で消去
→ 空になったことを確認
→ PostMessage(FLUTTERVIEW, WM_CHAR, ch) を1文字ずつ
→ 反映されるまでポーリング
→ 再生ボタンを accDoDefaultAction
```

`PostMessage` は宛先ウィンドウが前面である必要がないので、
**`SetForegroundWindow` / `SetFocus` / `SendKeys` を全て削除できました。**
検証中、前面ウィンドウは終始別アプリのままです。

副次的に、README の
「PotatoVoiceHub が Editor を操作中に PC を触ると正常に動作しない」
という制約もなくなります。

> **注意**: `/saveAudio` だけは Editor 側が書き出しダイアログを前面に出すため、
> フォーカスの移動が残ります。これは Editor の挙動なのでこちらからは制御できません。
> 元の前面ウィンドウを退避・復帰する処理は残してあります。

#### `Ctrl+Z` をやめた理由

`SendKeys("^z")` は Undo なので、直前の操作次第で消える量が変わります。
`VK_BACK` + `VK_DELETE` を文字数分送る方式に変えました。
再生直後はキャレットが文頭に戻っているため **`VK_BACK` だけでは1文字も消えません。**
`VK_DELETE` も同数送ることで、キャレットがどこにあっても確実に空になります。

#### 固定 `Sleep` をやめた理由

旧実装の `Thread.Sleep(aiv2SendKeysSleep)` は、
短すぎると1番目のメッセージが読まれず、長すぎると常に待たされる、という設定でした。

新実装では **入力欄の内容が期待どおりになるまでポーリング**し、
`aiv2SendKeysSleep` はその**上限**として使います。
反映され次第すぐ進むので、値を大きくしても普段の速度は変わりません。
設定ファイルの互換性のためフィールド名はそのままにし、設定画面の説明文だけ書き換えています。

### 4. `SanitizeText()` の縮小

**1段目（`{}~+^%\r\n"()` の削除）は撤廃しました。** SendKeys のエスケープ仕様回避のための処理で、
`WM_CHAR` では不要です。これらの文字がテキストから欠落しなくなります。

**2段目（句読点→カンマ）は残しました。** ただし対象を絞っています。

実機で確認したところ、**A.I.VOICE2 Editor はテキストを「文」に分割し、
再生ボタンは現在の文だけを再生します。** これは Editor 本体の挙動で、SendKeys とは無関係でした。

分割される文字を全角・半角ぜんぶ試して切り分けた結果:

| 文字 | 文を分割するか |
|---|---|
| `。` `｡` `？` `?` `！` `!` | **する** |
| `、` `､` `．` `.` 改行 | **しない** |

そこで **`、` `､` `．` `.` を置換対象から外しました。**
読点は文を分割しないので、置換しなくても全文読まれます。
これで読点の「間」が保たれるようになります（動作は変わらず、読み上げ品質だけ上がります）。

### 5. 「句読点を残して読み上げる」設定を追加（既定 OFF）

`。？！` を保ったまま全文を読む方法も見つかったので、設定で選べるようにしました。

```
再生 → 完了待ち → 「次の文」 → 再生 → … を文の数だけ繰り返す
```

イントネーションは自然になりますが、文の切れ目に **1文あたり約1秒**のオーバーヘッドが乗ります。
配信用途では遅延が気になると思うので、**既定は OFF（従来どおりカンマ置換）**にしています。

設定は `VoiceHubOption.aiv2KeepPunctuation` に増やしました。
**旧バージョンの設定ファイルにこの項目が無くても既定値で解決する**ようにしてあります
（`bool.TryParse` を使い、`readOption()` の `try` の中では読みません）。

### 6. プリセット（キャラクター）切替の実装

`//プリセットの機能は無し` となっていた箇所を埋めました。
`/play?preset=` `/saveAudio?preset=` が効くようになります。

2.14.1 で「テキストブロックに割り当てるキャラクター」を変える経路は、
メニューを3段たどるしかありませんでした。

```
メニュー[キャラクター] → [テキストブロックに割り当て] → [N番目のキャラクター]
```

- `Ctrl+1`〜`Ctrl+0` のショートカットは `PostMessage` では効きません
  （投げたメッセージでは修飾キーの状態が更新されないため）。メニューをたどる以外に手がありません。
- **メニューに項目が10個までしか無いので、一覧の11番目以降は切り替えられません。**
  この制限は設定画面にも書きました。
- 3段たどると **3秒前後**かかります。棒読みちゃんは1行ごとに preset を送ってくるので、
  **既に割り当たっているキャラクターなら何もせず返します**（実測 625ms。
  一覧と現在の割り当てを読むためにツリーを2回走査するぶんです）。

なお `Plugin_PotatoVoiceHub` は `/play?text=` しか投げないので、
現状 preset が効くのは curl などの直接呼び出しのみです。プラグイン側は触っていません。

### 7. 書き出し経路の作り直し

2.14.1 では `書き出し` を押すと **Windows の共通ダイアログ**（class `#32770`）が開きます。
旧実装が探していた `書き出しを実行` という要素は無くなっていました。

共通ダイアログは**コントロールID**で引くようにしました。IDはロケールにも Windows のバージョンにも
依存しないので、`AutomationId` や表示名より安定します。

| 対象 | 取得方法 |
|---|---|
| 保存 | `GetDlgItem(dlg, 1)`（IDOK） |
| キャンセル | `GetDlgItem(dlg, 2)`（IDCANCEL） |
| ファイル名欄 | ctrl id 1001 の `Edit`（`ComboBoxEx32` 配下の孫なので再帰検索） |

#### `/saveAudio?path=` が反映されるようにしました

ハンドラが `queryString["path"]` を読んでおらず、`SaveAudioAiv2(text)` にテキストしか
渡していなかったため、Editor が最後に使ったフォルダへ既定の名前で保存されていました。
**この点は現行 HEAD (`f3ba895`) から同じで、今回の変更で入った回帰ではありません。**

ファイル名欄にフルパスを `WM_SETTEXT` で書き込めば共通ダイアログ側が解決してくれるので、
フォルダを開き直す操作は不要でした。
書き込んだあと `WM_GETTEXT` で読み戻して一致を確認し、
**書き込めなかった場合は保存せずキャンセル**します
（既定のファイル名のまま保存すると意図しない場所に落ちるため）。

クリップボード経由の書き出しも同じ経路に載せ、`saveAudioPath` の
`{yyyyMMdd}` `{HHmmss}` `{VoicePreset}` `{Text}` を展開して渡すようにしました。

#### 同名ファイルへの上書き

保存先に同名ファイルがあると「名前を付けて保存の確認」が挟まって止まってしまうので、
出てきたら `はい` を押して進めるようにしました。

この確認は TaskDialog で、ボタンは実 HWND なのに `GetDlgCtrlID` が 0 を返すため
`GetDlgItem(h, IDYES)` では取れず、`WM_COMMAND(IDYES)` も `TDM_CLICK_BUTTON` も効きませんでした。
`Button` クラスの HWND へ直接 `PostMessage(BM_CLICK)` すれば押せます。

ただし**ボタンの数はダイアログの種類の判別にはなりません**。
保存先のエラーや別の警告が2ボタンで出てきた場合、それも肯定してしまいます。
そこで、保存を押す前に**ファイル名欄に入っている絶対パスが実在するか**を確認しておき、
上書きになると分かっているときだけ肯定するようにしました。

想定していない確認が出てきた場合は肯定せず、`WM_CLOSE`（TaskDialog では否定にあたります）で
閉じてから書き出し自体を中止し、`error` を返します。
ボタンがちょうど2つという条件も残していますが、これは保険です。

### 8. 待ち処理まわり

- **スピンウェイトの解消**: `SaveAudioAiv2()` の書き出しダイアログ待ちループに `Sleep` が
  入っておらず、最大10秒間 UIA 全走査を待ち無しで回していました。
  `Sleep(50)` を入れた待機に置き換えています。
- **`accDoDefaultAction` の取りこぼし対策**: `S_OK` が返ったのに Editor が反応しないケースを
  `書き出し` で1度観測しました。`StartPlay()` / `StartWrite()` は
  短めのタイムアウトで見切って**1回だけ押し直します**。
- **待ち続けない**: 再生ボタンが消えてしまう状態があり、
  「再生中でない」と判定し続けて 120 秒スピンする事故が起きました。
  ボタンの状態を `Missing` / `Idle` / `Busy` の3値で扱い、
  `Missing` が続いたら待機を打ち切ります。

### 9. `Thread.Abort()` の除去

`Window_Closing` の `threadClipboard.Abort()` を、フラグ + `Join(2000)` に置き換えました。
`Thread.Abort` は .NET Core 以降で `PlatformNotSupportedException` になるため、
将来 .NET へ移行する際のブロッカーになります。
併せて監視スレッドを `IsBackground = true` にし、`HttpListener` も閉じるようにしました。

ループ条件を `while (IsVisible)` からフラグへ変えたのは、**`Window_Closing` の時点では
まだ `IsVisible` が `true` だから**です。旧条件のままだと、閉じる処理の中で `Join` しても
監視スレッドは抜けません。実測では `Join(2000)` が 2,000ms 丸ごとタイムアウトし、
`IsVisible` が `false` になるのは `Closed` になってからでした。
`HttpListener` を閉じる前に監視スレッドを確実に止めたいので、
監視を続けるかどうかをウィンドウの可視状態から切り離しています。

（`IsVisible` 自体はワーカースレッドからでも読めます。`UIElement.IsVisible` の getter は
`GetValue` を通らず内部フラグを直接読むため `VerifyAccess()` が走りません。
一方、次の `WriteLog()` が触る `TextBox.Text` は通常の DependencyProperty で、
別スレッドから代入すると `InvalidOperationException` になります。両方とも実測で確認しました。）

### 10. クリップボード監視が1回の失敗で止まらないように

監視ループ全体を `try/catch` で囲み、例外が出てもログに残して次の周回へ進むようにしました。
また `WriteLog()` は監視スレッドからも呼ばれるため、`Dispatcher` 経由で UI スレッドへ回しています
（従来は例外になり、ログが出ないまま終わっていました）。

### 11. 動かないときに理由をログへ出す

今回の実装は **Editor 2.14 系の画面構成を前提**にしています。
構成の違うバージョンでは要素を引き当てられませんが、
黙って `busy` を返すだけだと利用者からは「何も起きない」ようにしか見えません。

そこで `GetAvailability()` を用意し、状態が変わったときだけログに出すようにしました。

```
A.I.VOICE2 Editor が見つかりません。Editor を起動してください。
A.I.VOICE2 Editor の画面を認識できないため、操作できません。動作を確認しているのは Editor 2.14 系です。
```

棒読みちゃんは1行ごとにリクエストを送ってくるので、**同じ理由は繰り返し出しません**。

### 12. 設定画面の文言を実態に合わせて更新

- 「再生や保存をする度に Editor が表示されます」→ 前面に出なくなった旨に変更
- 「セリフ入力欄を選択した状態にしておいてください」→ 不要になったので削除
- 「プリセット名は使えません」→ 使い方の説明に差し替え
- `aiv2SendKeysSleep` / `aiv2DelCount` の説明を新しい意味に合わせて書き直し
- 「句読点を残して読み上げる」チェックボックスを追加
- 「Editorの設定画面などを開いたままにすると読み上げが止まります」を追記

### 13. 書き出しの完了を待つように

これは実機で再検証していて見つけたものです。

**保存ダイアログが閉じても書き出しはまだ終わっていません。**
その間 Editor は進捗表示に切り替わり、**MSAA ツリーが 8 要素まで縮んでボタンが全部消えます**（実測 約2.3秒）。

```
経過ms   要素数   再生ボタン     書き出しボタン   ファイル
603      8       (無し)        (無し)         -
2023     8       (無し)        (無し)         -
2847     138     再生          書き出し        297276
```

そのため `/saveAudio` を連続で投げると、**2回目が「書き出しダイアログが表示されませんでした」で失敗**します
（前の書き出しが走っている最中なので `書き出し` ボタンを引き当てられない）。

厄介なのは、**ダイアログが閉じた直後の `IsEnabledPlay()` が `true` を返す**ことです。
進捗表示が出るまでに遅れがあるので、その瞬間だけ「空いている」ように見えます。

`WaitUntilWriteFinished()` を追加して、`AcceptSaveDialog()` のあとに
「進捗表示が出るのを待つ → 消えるのを待つ」の2段で待つようにしました。
ボタンが見えない状態は Editor が落ちたときと区別がつかないので、1段目は時間で区切り、
出ないまま過ぎたら完了済みとみなします。

### 14. Editor 起動直後の接続が失敗しないように

これも再検証で見つけたものです。Flutter はアクセシビリティの要求を受けて初めて
セマンティクスを構築するため、**その構築を引き起こした最初の1回だけ、
まだ組み上がっていないツリーが返ってきます。**

```
1回目 GetAvailability : ElementsNotFound   要素数=83   ← 直後の走査では取れている
2回目 GetAvailability : Ok                 要素数=83
```

`ConnectAiv2()` は `IsAvailable()` で接続を弾くので、Editor を起動してすぐ接続すると失敗します。
**一度も要素を引き当てられていない間だけ** 200ms × 最大5回リトライするようにしました。
組み上がったあとの失敗は Editor 側の異常なので待ちません。

### 15. 失敗したときに `ok` を返さないように

`/play` `/saveAudio` は結果によらず `{"status":"ok"}` を返していました。
呼び出し側からは「成功したはずなのに鳴らない・ファイルが無い」ようにしか見えないので、
`PlayAiv2()` / `SaveAudioAiv2()` を `bool` にして `{"status":"error"}` を返すようにしています。

**この変更は A.I.VOICE2 経路にのみ入れました。** A.I.VOICE1 側の `switch` は触っていません。

### 16. HTTP とクリップボード監視の直列化

Editor という1つの GUI を、HTTP の応答スレッドとクリップボード監視スレッドが共有しています。
「空いているか確認 → キャラクター切替 → セリフ投入 → 再生開始」を一まとまりにしないと、
両方が `IsEnabledPlay()` を通り抜けたあとで互いのセリフを上書きしてしまいます。
`Aiv2EditorElem` 側のロックは各メソッドの内側しか守らないので、
呼び出し側に `aiv2Sync` を置いて一連の操作を囲みました。

クリップボード側は、ロックを取ったあとで `IsEnabledPlay()` を見直します
（待っている間に HTTP 側が操作を始めていることがあるため）。
見直しで busy だった場合は**そのクリップボード内容を既読にしません**。
既読にしてしまうと、手が空いたあとも同じ内容は二度と読まれなくなります。
ただし A.I.VOICE1 も接続されていて既にそちらが読み上げている場合は、
次の周回でもう一度読まれてしまうので既読にします。

ループ先頭の busy 判定もロックの中に入れました。状態の読み取りは内部のキャッシュを
更新するので、ロックの外でやると HTTP スレッドの操作と並行してしまいます。
両エンジンをまとめて見る判定そのものは元のままです。

### 17. 状態を読めなかったときは「操作できる」と解釈しない

- `Aiv2Native.TryGetState()`: `get_accState` の例外時に `0`（＝フラグが何も立っていない）を返すと、
  呼び出し側からは「操作できる状態」と区別がつきません。成否を分けて返すようにしました。
- `GetPlayButtonState()`: 状態を読めなかった場合は `Busy` として扱います。
  読み上げ中に次の操作を始めてセリフを上書きするより、1回スキップするほうが安全です。
- `RewindToFirstSentence()`: テキストを読めなかった場合や `前の文` を押せなかった場合は、
  位置が分からないまま進まず `false` を返します
  （前述の不変条件を破ると Editor がエラー表示に切り替わってしまうため）。
  ただし押した結果は読めないので、**着いたことの確認ではありません**（18）。
- `SetPresetAiv2()`: キャラクターを切り替えられなかったらそこで止めて `error` を返します。
  そのまま続けると、直前に選ばれていた**別のキャラクターの声**で読み上げ・書き出しをして、
  呼び出し側からは指定どおりに処理されたようにしか見えません。
  （A.I.VOICE1 側は存在しないプリセット名を黙って無視して続行します。
  そちらは触っていないので、A.I.VOICE2 側だけ挙動が変わります。）

### 18. 「先頭の文へ戻す」を記憶ではなく毎回の操作で担保する

テキストを差し替える前に先頭の文へ戻さないと Editor が落ちる、という不変条件があります
（`RangeError (length): Invalid value: Only valid value is 0: 2`）。
当初は**戻した回数を数えてフラグで覚える**実装にしていましたが、これでは足りませんでした。

- `accDoDefaultAction` は S_OK を返しても稀に空振りします。文数ぶんちょうど押すだけでは、
  1回でも空振りすると先頭に着かないまま「着いた」ことになります
- Editor の「現在の文」は**ユーザーがセリフ入力欄をクリックしても動きます**。
  こちらの操作だけを数えていても実際の位置とはずれます

先頭に着いたかを状態から読めないかも調べましたが、`前の文` / `次の文` は
端に着いても `STATE_SYSTEM_UNAVAILABLE` が立たず、**位置は MSAA からは観測できません**。

そのため、位置は覚えず `SetText()` の直前に毎回押し直し、
**文数ぶんの倍（最低でも +2 回）**押します。
先頭で `前の文` を押しても何も起きないので、多めに押す側は安全です。
テキストが1文なら位置は先頭以外になりえないので1回も押しません
（句読点をカンマへ置換する既定の動作では常にこちらで、追加コストはゼロです）。

**これは保証ではありません。** 押した結果を読めない以上、必要な回数ぶん成功しなければ
先頭に着かないまま先へ進んでしまいます（3文以上なら「半分を超えて」空振りした場合、
2文なら最低 +2 回が効くので「3回とも」空振りした場合）。余分に押すぶんは
実測に基づく安全マージンで、文数に比例させているので許容できる空振り率は
文数によらず一定になります（固定で +2 回だと、文が増えるほどマージンが薄くなります）。
コメントにもそう書きました。

多めに押しても遅くはなっていません。200ms の待ちが要るのは
**移動してから `再生` を押すまで**で、移動を続けている間は要らないと実機で確認したので
（間隔0msで60回押しても取りこぼしゼロ）、連打して最後に1回だけ待つようにしました。
既存テキストの文数別の実測は、差し替え全体で 1文 147ms / 3文 386ms / 10文 456ms / 30文 703ms です。

押す回数には上限（1000回）を設けています。既存テキストが500文を超えている場合しか
当たりませんが、要求が何分もブロックされるのを防ぐためです。

**セリフ入力欄が外から書き換えられた場合は、巻き戻せる文数を先に用意します。**
空のテキストは1文と数えられるので、そのまま差し替えると
「1文だから巻き戻し不要」と判断してしまい、末尾に残った位置のまま
文数の少ないテキストへ差し替えることになります（＝防ごうとしている `RangeError`）。
入力欄を空にしても Editor 内部の位置は残り、文が1つしかないテキストでは
`前の文` が何もしないので、その場では戻せません（実機確認済み）。
表示が崩れたときの復旧手順として利用者に入力欄を空にしてもらう以上、これは実際に起きます。

判定はひとつだけです。**入力欄の中身がこちらの入れたものと一致するか。**

- **一致する**: 位置はその文数を超えません（こちらが入れて、こちらが再生したので）。
  そのまま巻き戻せます。**通常はこちら**で、追加コストはゼロです
- **一致しない**: 外から書き換えられている（か、接続後まだ一度も入れていない）。
  このとき**位置に上限を置けません**。利用者は文を増やしてから消すこともできるので、
  今の文数からも、こちらが最後に入れたテキストの文数からも「これだけあれば足りる」
  とは言えません。**100文の足場を敷いてから巻き戻します**

覚えるのは**テキストであって位置ではありません**。
何かの拍子に覚えを失っても足場の側へ倒れるので、余分に時間がかかるだけで判断は誤りません。

実測では足場の経路が 1.8〜2.1秒、次の要求からは通常経路（148ms）に戻ります。
通常の経路のコストは上表のままで増えていません。

承知のうえで残している穴が2つあります。どちらも踏むと `RangeError` になり、
Editor の再起動が必要です。

**(1) 位置が100文目より後ろから始まっていた場合は戻せません。**
足場をいくつ敷けば足りるかは位置が読めない以上わからないためです。

**(2) 一致は「その間に外から触られていない」ことの証明ではありません。**
文を増やして位置を進めたあと、**元と同じ文字列へ戻される**と素通りします。
実際に踏むには、要求と要求の間に「2文以上に増やす」「現在の文を先頭以外へ動かす」
「こちらが最後に入れた文字列へ1文字違わず戻す（現実的には Ctrl+Z）」を全部やる必要があります。

塞ぐには毎回足場を敷くしかありませんが、1回あたり約2秒かかります。
棒読みちゃんは1行ごとに要求を送ってくるので、常時2秒は載せられないと判断しました。
**足場なしで「多めに押す」では代用できません** — 文が1つしかないテキストでは
`前の文` が位置を動かさないので、足場を敷くことと押すことは切り離せないためです。

### 19. 待ち時間の上限まわりの補強

- 句読点を残すモードは文の数だけ再生を繰り返すので、1文ごとの上限だけでは
  リクエスト全体の長さを縛れません。全体の締切（5分）を追加し、
  個々の待ちにも**残り時間しか渡しません**。最後の1文だけ青天井になると締切の意味がなくなるためです。
  再生ボタンの押し直しも締切の内側で、押し直す前に残り時間を計算し直します。
  実測では締切 3,000ms 指定に対して 3,000〜3,009ms で打ち切れています。
  なお締切が掛かるのは再生の繰り返しだけで、その前の巻き戻し（18）は含みません。
  そちらは押す回数の上限（1000回・約40秒）で縛っています。
  締切は待ちに入る**前**に確認するので、待っている最中に来た締切には
  その待ちが終わってから気づきます。ポーリング間隔（20ms）ぶんは超えうる、
  という意味でのソフトな締切です。
- `/saveAudio?path=` は `Path.GetFullPath()` で絶対パスに直してから使います。
  相対パスのままだと、フォルダ作成はこちらの実行ディレクトリ基準、
  ファイル名欄の解決は共通ダイアログの現在フォルダ基準になり、別の場所を指しかねません。
  パスとして解釈できなければ保存せず `error` を返します。
- `path` が空の場合は従来どおり Editor の命名規則に任せます（ログには残します）。

### 制限事項

**読み上げ中にクリップボードが変わると、稀にその内容が読まれないまま既読になります
（upstream から変わりません）。** A.I.VOICE1 も接続されている場合、
2 が busy で処理できなかった内容は既読にします（16）。既読にしないと 100ms 後の周回で
同じ内容がまた未読として通り、A.I.VOICE1 が二度読み上げてしまうためです。

`aiv2Sync` の範囲を広げても直りません。このロックは**本アプリのスレッド同士**を
整理するもので、Editor を占有できるわけではないからです。利用者が Editor で手で再生を
押した場合や、`/play` が再生開始で返ったあと（句読点を残さない既定の動作）も
Editor は喋り続けるので、ロックの内側で busy を見ることは起こりえます。
そのうえループ本体には 1.x の書き出し（完了までブロックします）と
`Dispatcher.Invoke` が入るので、囲うと HTTP の応答が 1.x の都合で待たされ、
UI スレッドとのロック順序の面積も広がります。

**Editor の設定画面など、別ウィンドウを開いたままにしないでください。**
その間は `accSelect` によるフォーカス移動もキー入力も受け付けなくなり、読み上げが止まります。
閉じれば元に戻ります。設定画面の説明文にも書きました。

**`/saveAudio` は1回あたり2〜3秒ブロックします。**
書き出しの完了まで待つ（13）ぶんです。待たないと次の要求が失敗するので、
ここは短縮できませんでした。`/play` は従来どおり再生開始で返します。

**セリフ入力欄を外から編集したあと、こちらが最後に入れた文字列へ1文字違わず戻すと、
巻き戻しの足場を敷き損ねます。** 実際に踏むには、要求と要求の間に「2文以上に増やす」
「現在の文を先頭以外へ動かす」「元と同じ文字列へ戻す（現実的には Ctrl+Z）」を
全部やる必要があります。位置が100文目より後ろから始まっていた場合も同様に戻せません。
どちらも踏むと Editor の再起動が必要です。理由と、常時足場を敷かなかった判断は 18 に書きました。

**稀に、Editor の表示が崩れて再生系のボタンが全部消えることがあります（この変更とは無関係）。**
文数の多いテキストで文を送っていると、アクセント編集ペインが画面のはるか下
（`アクセント` タブの screen Y が 987 → 175910）へ飛び、`再生` / `前の文` / `次の文` /
`書き出し` がまとめて MSAA ツリーから消えます。Flutter のエラー画面とは別物で、
メニューバーもキャラクター一覧も生きています。**セリフ入力欄を空にすれば元に戻ります。**

この状態では 18 の巻き戻しができないので、以降の要求は失敗し続けます。
意図的にそうしています。ここで自動的にテキストを消しても、消しただけでは
「現在の文」の位置が残るので復旧にならないためです。
発生条件を任意に再現できず（同じ手順を12回繰り返しても再現しないことがあります）、
自動復帰は通しで検証できないため入れていません。ログには入力欄を空にするよう出します。

利用者が入力欄を空にすれば表示は戻ります。**そのあと位置が残る問題は
18 の「文数を取り戻してから巻き戻す」経路が引き受ける**ので、
案内どおりに空にしてもらって差し支えありません。

### 実装時の注意点

`Aiv2EditorElem` は「テキストを差し替える前に必ず先頭の文へ戻す」という不変条件を持っています
（`SetText()` の先頭で `RewindToFirstSentence()` を呼びます）。

Editor は「現在どの文を選んでいるか」をテキストを差し替えても保持するため、
これを守らないと Editor 側で範囲外アクセスが起きて画面がエラー表示に切り替わってしまいます。
手で Editor を使っている限りは起きない、外部からの自動操作に固有の話です。
コードを触る際はこの不変条件を崩さないようご注意ください。

**位置を変数で覚えないでください。** 現在の文はユーザーが入力欄をクリックしても動き、
`accDoDefaultAction` も稀に空振りします。位置は MSAA からは読めないので
（18 のとおり、端でもボタンの状態は変わりません）、
差し替えの直前に毎回、文数より多めに押す以外の方法がありません。

## 気づいた点（今回は変更していません）

`initHttp()` の待ち受けが `http://+:<port>/` で、**LAN 上の他ホストからも届きます**。
具体的な内容や再現手順の記載は避けたいと思います。

`app.manifest` が `requireAdministrator` なので、すべて管理者権限で行われます。

これらは `f3ba895` の時点からある挙動です。

`http://localhost:<port>/` に絞れば塞げますが、**別マシンの棒読みちゃんから叩いている方がいる可能性**があり、
勝手に変えると壊してしまうので手を付けていません。
待ち受けアドレスを設定で選べるようにする、保存先を特定フォルダ配下に限る、README に注意書きを置く、
といった選択肢があると思いますが、既存の利用者への影響が大きいので判断はお任せします。
